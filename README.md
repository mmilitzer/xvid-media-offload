# Media Local Offload

## Purpose

This project provides a Linux service and CLI tool that reduces local disk usage for large MP4 media files that are already stored remotely by our Xvid MediaHub media conversion and publishing service.

Some customer CMS installations require generated media files to remain present in the local site filesystem even though the live website serves those files from CDN/cloud storage. This tool keeps those files visible to the CMS while freeing most of the local disk space.

## Core idea

The tool does not fully delete local MP4 files. Instead, it keeps the beginning of the file intact and uses filesystem hole punching to deallocate most of the remaining file while preserving the original logical file size.

This means:

- the CMS still sees the file at the original path
- `stat()` still reports the original file size
- the beginning of the MP4 remains available for metadata probing (duration, resolution, etc.)
- most local disk blocks are freed
- the full file can later be restored from remote MediaHub storage

The MP4 files handled by this tool are generated by our MediaHub service and are known to be optimized for streaming, with MP4 metadata located near the beginning of the file.

## Customer-facing restore mechanism

When a file is offloaded, the tool creates a sibling marker file:

```text
filename.mp4.offloaded
```

For customers, the rule is simple:

> The video file is still present for the CMS, but most of its local disk space has been freed. Delete the matching `.offloaded` file to restore the full local video file from cloud storage.

This fits customers who manage their site files with FTP/SFTP clients rather than SSH or command-line tools.

## Important design principles

### Filesystem-first design

The filesystem is the primary source of truth.

The service should be able to recover useful state by scanning the configured directory trees, reading the .htaccess content marker files, detecting `.offloaded` companion files, detecting sparse MP4 files, and detecting interrupted restore temp files.

A local sqlite database may be used later as a fallback, audit log, or cache, but the system should not depend on the database for normal operation.

### No database for ordinary candidates

Files that merely could be offloaded should not be persisted as database rows.

A candidate is just something found during a scan. If it is old enough and eligible, it can be offloaded immediately in a later milestone. If it is not old enough, it should simply be ignored until a future scan.

### Minimal persistent state

Persistent state should only be used for files that were actually modified by the tool, for example files that were offloaded.

Even then, the first implementation should avoid unnecessary state machines. Most restore work can be represented as in-memory jobs rebuilt from filesystem reality during scans.

### No mounts

This project intentionally avoids FUSE, OverlayFS, bind mounts, or other mount-layer tricks in the initial product direction.

The first implementation should work directly on the existing local filesystem.

## Filesystem requirements

The offload mechanism relies on Linux hole punching:

```text
fallocate(FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE)
```

This keeps the apparent file size unchanged while freeing allocated disk blocks from the punched range. Common Linux filesystems such as ext4, XFS, and Btrfs support this.

The tool should detect unsupported filesystems safely and skip offloading rather than damaging files.

## Marker files

Each content folder generated by our system contains a .htaccess marker file. The marker file proves that the folder belongs to our system and contains the remote file identifiers needed to restore generated media files.

The marker file is valid only if the first line is exactly:

```text
#Xvid AutoGraph content protection system.
```

If this first line does not match exactly, the folder must be ignored.

The marker file also contains mappings from local media filenames to remote file ids. Example:

```text
#Xvid AutoGraph content protection system.
#Removing or renaming this file will disable all content protections.
#Do not ever remove this file unless you know *exactly* what you are doing!!
RewriteEngine on
RewriteRule "^720p/abc1161.mp4" - [F,L,NC]
RewriteRule "^720p/.*\.m4s$" - [F,L,NC]
#autograph=1
#pipeline_id=60edcc62e4b006349ae79ab9
#file_id=669872d3d3586a56f9a3dfad
#object_key=/abc1161/720p/abc1161.mp4
RewriteEngine on
RewriteRule "^1080p/abc1161.mp4" - [F,L,NC]
RewriteRule "^1080p/.*\.m4s$" - [F,L,NC]
#autograph=1
#pipeline_id=60edcc62e4b006349ae79ab9
#file_id=669872d3d3586a56f9a3dfbf
#object_key=/abc1161/1080p/abc1161.mp4
```

There can be a variable amount of different videos (different resolutions) listed in the marker file, not just two like in the above example. It can also occur that there are duplicate entries, so that the same regexp (and object key) appear multiple times but with different file ids. In this case, the last occurrence (when reading from first to last line) in the marker file should "win", so the last entry's file id is to be used.

## Configuration

The tool should use a config file. YAML is acceptable for the initial implementation.

Example:

```yaml
scan_roots:
  - /home/html/site_root/content

candidate_globs:
  - "**/4k/*.mp4"

marker_filename: ".htaccess"
marker_depth: 1

minimum_age: "720h"

keep_prefix_bytes: 52428800

scan_interval: "24h"

restore_workers: 4

# Optional, for later milestones only.
database_path: "/var/lib/media-offload/media-offload.db"
```

The first milestone only needs enough config to scan and report candidates.

`marker_depth` controls how many directory levels below `scan_roots` the tool looks for marker files. The default is `1` (e.g. `content/set1/.htaccess`). Use `2` for layouts like `content/group1/set1/.htaccess`.

## Candidate rules

A file may be considered an offload candidate only if all of the following are true:

- it is under a configured scan root
- it is inside a folder with a valid .htaccess marker file
- it is a regular file
- it has a `.mp4` extension
- it matches one of the configured candidate globs
- it is older than the configured minimum age
- the .htaccess marker file contains a matching remote file id for it (Rewrite engine regexp matches the file)
- it does not already have a sibling `filename.mp4.offloaded` marker, so it's not already offloaded

Sparse-file detection and actual offloading are planned for later milestones.

## Intended lifecycle

### Scan

The tool scans configured directory trees, identifies managed folders using marker files, finds eligible MP4 files and parses out their remote file ids.

### Offload

A later milestone will offload eligible files by:

1. preserving the first `keep_prefix_bytes` bytes
2. punching a hole from that offset to the end while keeping logical file size unchanged
3. creating `filename.mp4.offloaded`
4. optionally storing minimal fallback metadata in a local sqlite DB

### Restore

A later milestone will restore files when `filename.mp4.offloaded` is deleted.

The restore service will:

1. detect `filename.mp4.offloaded` deletion, through inotify or period re-scan of configured scan roots
2. determine the remote file id from the folder marker file, or fallback metadata from sqlite DB if necessary
3. check available disk space
4. download the full file to a temporary sibling path such as `filename.mp4.restore.<uuid>.tmp`
5. verify size/checksum where available
6. fsync the temporary file
7. atomically rename the temporary file over the sparse MP4
8. fsync the directory
9. leave the restored file with a fresh mtime so it is not immediately offloaded again

If there is not enough disk space to restore, the service should recreate the `.offloaded` marker and leave the file in the offloaded state.

## Implementation requirements

- Language: Go
- No CGo dependency
- Target platform: Linux
- Prefer standard library plus small, well-maintained dependencies
- Use `golang.org/x/sys/unix` for Linux syscalls when needed
- Use `modernc.org/sqlite` if/when SQLite is introduced
- The project should build with `CGO_ENABLED=0`
- Destructive operations must be opt-in
- Dry-run mode must be supported for scanner/offload commands
- Operations should be idempotent and crash-recoverable
- The daemon should run as an unprivileged user when file permissions allow it

## Suggested command shape

Initial command:

```bash
media-offload scan --config ./config.yaml --dry-run
```

Future commands:

```bash
media-offload offload --config ./config.yaml --dry-run
media-offload offload --config ./config.yaml --apply
media-offload restore /path/to/file.mp4
media-offload daemon --config ./config.yaml
media-offload status --config ./config.yaml
```

## Initial milestones

### Milestone 1: scanner CLI

Implement config parsing, marker validation, marker parsing, candidate discovery, dry-run reporting, and tests.

No file modifications. No database required. No daemon mode.

### Milestone 2: hole punching and `.offloaded` marker creation

Add sparse-file detection, filesystem capability test, hole punching, `.offloaded` marker creation (and adding entry into local DB), and idempotent offload behavior.

### Milestone 3: restore service

Add in-memory restore queue, restore-on-marker-deletion behavior, full-file download, temp file handling, atomic replacement, disk-space checks, and crash reconciliation.

### Milestone 4: daemon mode

Add periodic scans, inotify watches, config reload, worker pools, logging, and systemd unit files.

## Safety rules

- Never modify a file unless its folder has a valid marker file.
- Never modify a file unless its remote file id is known.
- Never modify files in dry-run mode.
- Never treat all MP4 files as ours.
- Never rely on the DB as the only source of truth.
- Prefer filesystem reality over cached state.
- Keep restore and offload operations atomic where possible.
- Be conservative when disk space is low.
